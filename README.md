# 🔥 MMR Oracle — анализ потенциального MMR в Dota 2

Premium-платформа аналитики Dota 2: вставьте ссылку на Steam / Dotabuff / OpenDota профиль
и текущий MMR — движок проанализирует **последние 200 рейтинговых матчей** и рассчитает:

- 🎯 **потенциальный MMR ± погрешность** (общий и по каждой из 5 позиций);
- 📅 **прогноз с датой** — когда при текущем темпе вы выйдете на потолок;
- 🏆 лучшие и худшие роли + рекомендацию, где апать быстрее всего;
- ⚔️ лучших героев, героев с **переоценённым винрейтом** и героев с высоким импактом;
- 📈 серии побед/поражений и стабильность игры по стрикам;
- 🧠 текстовые инсайты модели;
- 🔗 shareable-страницу результата.

### Почему OpenDota

Источник выбирался из Steam API / OpenDota / Stratz / парсинга Dotabuff:

- **OpenDota** — открытый REST API поверх реплеев и Game Coordinator: отдаёт до 200 матчей
  одним запросом с GPM/XPM/уроном/лайнами, имеет публичные константы героев и щадящие
  лимиты (60 req/мин бесплатно, больше по ключу). Легален и стабилен. ✅
- Steam Web API отдаёт только «сырой» список матчей без статистики по игроку — пришлось бы
  делать 200 запросов деталей.
- Stratz (GraphQL) — хорош, но требует токен для любого запроса.
- Парсинг Dotabuff нарушает их ToS и ломается при каждом редизайне. ❌

## Математическая модель

Полная реализация — `src/lib/engine/`.

### 1. Кривая winrate → MMR (жёсткие diminishing returns)

```
Δ MMR = 1150 · tanh((WR% − 50) / 12)
```

| WR | Δ MMR |
|---|---|
| 50% | 0 |
| 52% | +190 |
| 55% | +455 |
| 60% | +785 |
| 65% | +975 |
| 70% | +1070 |
| 45% | −455 |

Чем выше винрейт, тем дешевле каждый следующий процент базовой кривой.
Кривая симметрична, поэтому отрицательный винрейт опускает потенциал
**ниже** текущего MMR.

### 1b. Зона доминации (устойчиво экстремальный винрейт)

Устойчивые 65–90% винрейта означают, что игрок «не в своей лиге» —
базовой кривой тут мало. Поверх неё работает логистический бонус:

```
dom = 7000 · (σ(WRraw*) − σ(50%)) · min(1, игр/100) · (0.7 + 0.3·min(1, MMR/6000))
σ(x) = 1 / (1 + e^−(x−68%)/5.5%)
```

Ключевое: **WRraw\*** — это *сырой* винрейт всей выборки (без веса
свежести), ужатый 20 псевдоиграми, плюс рампа по числу игр. Поэтому 80%
за последние 20 игр почти не двигают бонус, а 80% на дистанции в 200 игр
раскрывают его полностью. Ниже 50% бонус зеркален (штраф, кэп −3500).

Контрольные точки (200 игр): 5000 MMR + 65% → **~7750** · 1000 MMR +
80% → **~6350** · 5000 MMR + 25% → **~400** · 80% только в последних
20 играх при 50% в остальных → бонус ~+150.

Для ролей зона доминации включается **только если 20+ игр набраны внутри
окна из 200 матчей**. Роль, добранная из старой истории, не получает ни
взлёта, ни обвала — старый винрейт не говорит о текущем уровне; для неё
работает только базовая кривая.

### 2. Вес свежих игр (лестница)

Последние **20 игр** весят одинаково — полный вес 1.0. Дальше каждые
**10 игр** вес умножается на 0.85: игры 21–30 → ×0.85, 31–40 → ×0.72,
41–50 → ×0.61 и т.д. Для ролей лестница считается по номеру игры
*на этой роли*.

### 3. Байесовское сжатие выборки

`WR* = (Σw·win + C·0.5) / (Σw + C)` — в выборку подмешиваются `C` псевдоигр
с винрейтом 50% (C = 10 общий, 8 на роль и на героя). «3 игры, 100% WR»
больше не даёт +900 MMR.

### 4. Стабильность и погрешность

Оценка выдаётся как **потенциал ± погрешность**.

- **Стабильность (0–100)** считается по стрикам: последовательность W/L
  режется на серии, серии от 3 игр дают очки `длина − 2`. Если у игрока
  есть и винстрики, и лузстрики — это «качели», парная часть считается
  с двойным весом; лузстрики сверх парных — тильт с меньшим весом;
  одни винстрики без лузстриков стабильность **не** снижают, как и полное
  отсутствие серий. Калибровка: монетка 50% ≈ 50 очков, строгое
  чередование → 100, блоки по 10 побед/поражений → ~0.
- **Погрешность** = `50 + (100 − стабильность)·3 + поправка за малую выборку`
  (до +200 MMR при 20 играх), округляется до 25.

### 5. Импакт и роль

- **Импакт (0–100)**: KDA, GPM, XPM, урон по героям/строениям и саппорт-метрики
  нормируются на **бенчмарки конкретной роли**; перебор смертей режет до 30% очков.
- **Модификатор сложности роли**: мид 1.05, керри 1.00, оффлейн 0.98, роумер 0.95, фулл-саппорт 0.92.

### 6. Итог

```
Потенциал = clamp( MMR + Δ(WR*)·roleMod + clamp((импакт−52)·5, ±150)
                        + clamp((стабильность−55)·1.5, ±90), 0…15000 )
```

- Герой: то же + фактор мастерства `min(1, games/15)`.
- **Прогноз даты**: темп игр/день берётся из окна анализа, дата выхода на
  потолок — из экспоненциальной модели подъёма (τ = 110 игр).

### 7. Добор ролей из истории

Основное окно анализа — последние 200 рейтинговых матчей. Если на какой-то
роли внутри окна меньше 20 игр (например, 8 матчей на саппорте), движок
постранично догружает **более старые** матчи (до 1000 вглубь) и дополняет
эту роль до 20 игр:

- добранные игры влияют **только** на карточку этой роли — общий потенциал,
  тренды, герои и сводка матчей считаются строго по окну из 200;
- вес свежести для ролей считается по номеру игры *на этой роли*, поэтому
  добранные матчи реально участвуют в оценке, а не обнуляются затуханием;
- доля старых игр расширяет погрешность роли, а в карточке показывается
  пометка «+N из истории»;
- если даже в глубокой истории 20 игр не набралось → «Недостаточно данных».

### Определение позиции

OpenDota не отдаёт позицию напрямую — она восстанавливается из `lane_role`
(для спарсенных реплеев), `is_roaming`, приоритета фарма (GPM/ластхиты) и
архетипа героя: саппорт на сейф-лейне → pos 5, кор на оффлейне → pos 3 и т.д.

## API

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/api/analyze` | `{ profile, currentMmr }` → `{ shareId, result }` |
| `GET` | `/api/analysis/:shareId` | Сохранённый снапшот для share-ссылок |

Ошибки типизированы: `PRIVATE_PROFILE`, `ACCOUNT_NOT_FOUND`, `NO_RANKED_MATCHES`,
`RATE_LIMITED`, `UPSTREAM_RATE_LIMITED` и т.д. — фронтенд показывает каждую
своим состоянием. Rate limit: 6 анализов/мин с IP; повторный запрос того же
аккаунта в течение 30 минут отдаётся из кэша без похода в OpenDota.

```
src/
├── app/                      # App Router: страницы, API-роуты, SEO (sitemap/robots)
│   ├── page.tsx              # лендинг: hero, форма, превью, формула
│   ├── analysis/[id]/        # shareable-страница результата
│   └── api/                  # POST /analyze · GET /analysis/[id]
├── components/
│   ├── ui/                   # shadcn-style примитивы (button, card, input…)
│   ├── home/                 # hero-секция, анимированный фон, форма
│   ├── analysis/             # дашборд: карточки, графики, медали, инсайты
│   └── layout/               # navbar, footer
└── lib/
    ├── engine/               # ⚙️ analytics engine: кривая MMR, роли, герои, инсайты
    ├── opendota/             # типизированный API-клиент + кэш констант
    ├── analysis-service.ts   # оркестрация: кэш → БД → движок → персист
    ├── steam.ts              # парсинг ссылок Steam/Dotabuff/OpenDota, vanity resolve
    ├── rate-limit.ts         # sliding-window limiter
    └── prisma.ts / cache.ts  # инфраструктура
```

Принципы: движок — чистые функции без I/O (легко тестировать), API-клиент
изолирован, UI получает готовый типизированный `AnalysisResult`. Для
горизонтального масштабирования in-memory кэш/limiter заменяются на Redis
за тем же интерфейсом.

## Деплой на Vercel

Проект работает на Vercel из коробки (`npm run build` уже включает
`prisma generate`). Что настроить:

1. **Переменные окружения** (Project → Settings → Environment Variables):
   `DATABASE_URL` (см. ниже), опционально `OPENDOTA_API_KEY`,
   `STEAM_API_KEY` и `NEXT_PUBLIC_APP_URL` (URL вашего домена — для
   корректных share-ссылок и SEO).
2. **База**: возьмите serverless-Postgres — Vercel Postgres / Neon /
   Supabase — и вставьте её строку подключения в `DATABASE_URL`
   (для Neon/Supabase используйте pooled-строку подключения).
   Один раз примените схему локально:
   `DATABASE_URL="<строка от провайдера>" npx prisma db push`.
   Без БД сайт тоже работает — не будет только share-ссылок и кэша.
3. **Лимит функции**: у `/api/analyze` выставлен `maxDuration = 60` —
   анализ с добором ролей может идти 15–30 секунд.

Нюанс: in-memory кэш и rate-limit на serverless живут в рамках одного
инстанса функции — для серьёзной нагрузки замените их на Redis
(интерфейсы в `src/lib/cache.ts` и `src/lib/rate-limit.ts` минимальные).

## База данных

Сайт использует **PostgreSQL** (поднимается docker-compose'ом, данные живут
в volume `pgdata`). Схема — `prisma/schema.prisma`, две таблицы:

| Таблица | Что хранит |
|---|---|
| `Analysis` | Снапшоты анализов: `shareId` (короткий id для share-ссылок), `accountId`, ник, аватар, `currentMmr`, весь результат в JSON-поле `result`, дата. Повторный запрос того же аккаунта в течение 30 минут отдаётся отсюда без похода в OpenDota. |
| `ApiCache` | Кэш констант OpenDota (список героев), TTL 24 часа. |

Как посмотреть данные:

```bash
# 1. Prisma Studio — визуальный браузер таблиц (удобнее всего)
npm run db:studio          # откроется http://localhost:5555

# 2. psql внутри docker-контейнера
docker compose exec db psql -U postgres -d mmr_oracle
#   \dt                    — список таблиц
#   SELECT "shareId", "personaName", "currentMmr", "createdAt"
#     FROM "Analysis" ORDER BY "createdAt" DESC LIMIT 10;

# 3. Любой GUI (TablePlus, DBeaver, pgAdmin) по строке подключения
#    postgresql://postgres:postgres@localhost:5432/mmr_oracle
```

Если приложение запущено без БД, анализ всё равно работает — не будут
только сохраняться share-ссылки и серверный кэш.

## Диагностика (Troubleshooting)

**«Не удалось связаться с OpenDota» / «Источник данных недоступен»** — серверная
часть не смогла выполнить запрос к `api.opendota.com`. Откройте
**`http://localhost:3000/api/health`** — эндпоинт проверит доступ к OpenDota и
базе данных и покажет точную причину (таймаут, DNS, отказ соединения) с
подсказками. Типичные случаи:

- **Нет интернета у контейнера/сервера** — проверьте
  `docker exec <container> wget -qO- https://api.opendota.com/api/constants/patch`.
- **Сломанный IPv6 в Docker-сети** — хост резолвит AAAA-записи, но IPv6 не
  маршрутизируется, и fetch зависает. В Dockerfile уже включён
  `NODE_OPTIONS=--dns-result-order=ipv4first`; после обновления пересоберите
  образ: `docker compose up --build`. При запуске без Docker добавьте эту
  переменную окружения вручную.
- **Корпоративный прокси / файрвол** — Node fetch не читает системные
  настройки прокси; исходящий HTTPS к `api.opendota.com` должен быть разрешён
  напрямую.
- **OpenDota действительно лежит или отдаёт 5xx** — бывает редко; клиент сам
  делает 3 попытки с бэкоффом, дальше просто подождите. Статус:
  https://www.opendota.com.

Ошибки сети теперь логируются с первопричиной (`ENOTFOUND`, `ETIMEDOUT`,
`ECONNREFUSED`…) — смотрите вывод `docker compose logs web` или консоль
`npm run dev`.
